# Минимальная аналитика и экономика

`lead-parser analytics` строит отчёт за период из отдельного согласованного snapshot SQLite. Команда не требует конфигурации или API-ключей, не обращается к сети и не изменяет базу. Поддерживается текущая схема SQLite 1. Веб-панели и новых таблиц в рабочей БД нет.

## Данные для первого отчёта по проду

1. SHA/версия установленного приложения, дата snapshot и период работы: `main` может отличаться от версии на сервере.
2. Snapshot через SQLite backup API. Обычный `cp` работающей WAL-базы может потерять последние записи. Оператор текущей версии может использовать `lead-parser --config /var/lib/parser/config.yaml --backup /absolute/new/snapshot.sqlite3`. Путь назначения должен быть новым; при занятой блокировке повторить после завершения сбора.
3. Если расходы уже собирались — копия `<storage.database>.usage.jsonl`. Для согласованной копии дождаться завершения сбора и online evaluation. Backup SQLite этот отдельный файл не включает.
4. Выгрузка OpenRouter Activity за тот же период с выделенным API-ключом проекта: [экспорт CSV/PDF](https://openrouter.ai/docs/cookbook/administration/activity-export). Общие расходы аккаунта с другими проектами не подходят. При BYOK дополнительно нужен счёт провайдера: OpenRouter показывает оценку внешних расходов, которая не обязательно совпадает со счётом.
5. Фактические расходы на сервер, прокси, браузерные сервисы и другие используемые подписки, с долей проекта и выбранного периода. Разовые работы разработчика учитывать отдельно от регулярных расходов.
6. Для оценки качества — поступившие заявки и ручные оценки. Для экономики продаж нужны статусы сделок, выручка и маржа; текущая база их не содержит.

Достаточно доступа на чтение или этих выгрузок. Рабочие ключи и `.env` для расчёта не нужны. Snapshot и отчёт с заявками содержат рабочие данные: хранить их в закрытом каталоге `reports/`, исключённом из Git.

## Построение отчёта

`--from` включительно, `--to` исключительно. По умолчанию используется UTC; часовой пояс бизнеса задаётся через `--timezone`. Пример ниже охватывает 1–9 октября по Москве; это пример команды, а не результаты прода.

```bash
uv run --locked lead-parser analytics \
  --database /absolute/private/snapshot.sqlite3 \
  --from 2026-10-01 --to 2026-10-10 --timezone Europe/Moscow \
  --usage-log /absolute/private/parser.sqlite3.usage.jsonl
```

Без `--usage-log` используется `<путь snapshot>.usage.jsonl`; отсутствие файла отражается в отчёте. Для JSON добавить `--format json`; для списка принятых заявок со ссылками, источниками и оценками — `--include-leads`. Поля `phone` и `text` не экспортируются, но пояснение ИИ может содержать фрагменты заявки. Отчёт выводится в stdout; при сохранении через перенаправление сначала установить `umask 077`. База должна быть самостоятельным backup, а не работающей БД с WAL.

Полная стоимость рассчитывается при передаче **фактических сумм за выбранный период**:

```bash
# Заменить суммы примера фактическими расходами из счетов.
uv run --locked lead-parser analytics \
  --database /absolute/private/snapshot.sqlite3 \
  --from 2026-10-01 --to 2026-10-10 --timezone Europe/Moscow \
  --ai-cost-usd 1.25 --fixed-cost-usd 4.50 --format json
```

`--ai-cost-usd` заменяет сумму журнала для расчёта, а не прибавляется к ней. Включить сюда расходы ИИ проекта за период, в том числе online evaluation и внешний BYOK, если они относятся к проекту. `--fixed-cost-usd` — прочие затраты, уже распределённые на проект и период. Нулевые расходы указывать явно как `0`. Суммы задаются в USD; другие валюты сначала привести по выбранному и зафиксированному курсу. CLI не подставляет тарифы, курсы или месячную стоимость сервера автоматически.

## Значение показателей

| Показатель | Смысл |
| --- | --- |
| Новые кандидаты | Уникальные `source:external_id`, впервые сохранённые в периоде после раннего отбора. Это не число всех просмотренных публикаций и не уникальные люди. |
| accepted / rejected / pending / review | Текущие состояния этих кандидатов на момент snapshot. При выключенном ИИ accepted не означает проверку моделью. |
| Ручная проверка | Текущая метка человека отдельно от оценки ИИ. Размеченная часть может быть нерепрезентативной. |
| Доставки когорты | Какие кандидаты периода уже доставлены на момент snapshot, с разбивкой по каналам. Один лид нескольким получателям не превращается в несколько лидов. |
| Первые доставки в периоде | Лиды, у которых первая подтверждённая доставка в любой канал произошла в периоде, включая кандидатов прежних периодов. Это знаменатель операционной стоимости лида. |
| Известные расходы ИИ | Сумма зарегистрированных `usage.cost`, отдельно от запросов с неизвестной ценой. Пропуски и отсутствие журнала не считаются нулевыми расходами. |
| Полная стоимость и стоимость лида | `(ИИ + прочие расходы периода) / первые доставки периода`. Рассчитывается только при явно заданных обеих суммах; при нуле доставок стоимость лида не определена. |

Стоимость лида — операционный показатель периода, а не точная себестоимость каждого кандидата: запросы ИИ и доставки могут относиться к разным когортам. Успех любого канала означает доставку хотя бы в Sheets или Telegram, не обязательную доставку всем адресатам. Состояния и ручные оценки хранят последнее значение; отчёт за прошлый месяц не восстанавливает их состояние на конец того месяца. Истории всех просмотров источников нет, поэтому историческая конверсия «просмотр → лид» не рассчитывается.

Разбивка по источникам показывает количество и текущие результаты кандидатов. Точная стоимость источника не выводится: один запрос ИИ может содержать кандидатов из разных источников. Модельная оценка не означает подтверждённый спрос, продажу или прибыль. CAC/ROI без сделок не рассчитываются.

Для выводов по проду отдельно просмотреть выборку заявок: реальный запрос исполнителя, нужный город/вид работ, свежесть, реклама и повторы между площадками. Итог анализа: затраты и стоимость лида, качество и состав заявок, результативные источники, потери на фильтрации/доставке и конкретные изменения для следующего периода. Синтетический evaluation-набор не заменяет эту проверку.

## Журнал после обновления

Обычный запуск и `evaluate --online` пишут `<storage.database>.usage.jsonl`. Каталог должен быть разрешён для записи runtime-пользователю. Схема SQLite остаётся 1; журнал переживает смену релиза, если БД расположена вне кода. `purpose=evaluation` отделяет тестовый корпус от pipeline-расходов.

Каждый HTTP-запрос получает начало и завершение с общим `request_id`: время UTC, модель, размер пачки, входные/выходные токены, известная стоимость и технический результат. Цена сохраняется и при непригодном ответе модели. Повтор — самостоятельный запрос. Промпты, тексты, контакты, ключи и полные ответы API не записываются. Файл создаётся с правами 0600; записи блокируются и синхронизируются на диск.

Цена берётся из [OpenRouter usage accounting](https://openrouter.ai/docs/cookbook/administration/usage-accounting), поля `usage.cost`, без дополнительных запросов. Это списание с аккаунта OpenRouter; внешние BYOK-счета и комиссии пополнения могут требовать отдельного учёта. По длине текста или текущему тарифу цена не оценивается.

Если начало записать невозможно, платный запрос не отправляется. Ошибка записи завершения отмечается в техническом логе и не отменяет успешную классификацию. Незавершённые запросы, таймауты, пропущенная цена и повреждённые строки показывают неполноту данных. Итог нужно сверять со счетами: журнал начинается только после установки этой версии и не доказывает полноту старой истории. Потерянный журнал из SQLite не восстанавливается.

Автоматической ротации нет. Перед архивированием дождаться завершения процессов и сохранить журнал вместе со snapshot. Части журнала за период можно объединить: отчёт сопоставляет записи по `request_id`, повторное включение той же записи не увеличивает стоимость. Исходные журналы сохранять до сверки и backup.
