# CI/CD и выкладка по тегу

[Parser checks](../.github/workflows/checks.yml) запускается при push **любой ветки**, при PR в `main` и вручную. Для старых веток, созданных до обновления workflow, сначала включите свежий `main`: события push используют workflow самой ветки. CI проверяет Python 3.12–3.14: Ruff, тесты, конфигурацию, offline evaluation, Git-историю на известные секреты, lock/export и установку собранного wheel вне checkout. Дополнительно установленный пакет мигрирует старую SQLite, запускает веб-сервис, проверяет `/healthz` и завершает процесс через SIGTERM. Рабочие API и секреты CI не использует.

[Deploy tagged release](../.github/workflows/deploy.yml) запускается только при push тега `vX.Y.Z`. Обычный push кода на сервер ничего не выкладывает. Версия тега должна совпасть с `project.version`, а коммит — входить в историю `origin/main`. Проверка отклоняет prerelease-суффиксы и ведущие нули. После проверки тега повторяется весь CI, собирается архив wheel + requirements с хешами + manifest, затем он передаётся по SSH. Два деплоя одновременно не выполняются.

Версия кода подготовлена как `0.2.0`; создание тега и первый рабочий деплой выполняются отдельно. Зелёный CI не подтверждает доступность реальных источников и качество модели на проде.

## Однократная подготовка сервера

Нужны Linux/systemd, Python 3.12 с `venv`/`pip`, runtime-пользователь `parser` и доступ к закреплённым Python-зависимостям. Для локального Chromium установите системные библиотеки Playwright; CDP собственного Chromium не требует.

Размещение по умолчанию:

```text
/opt/parser/releases/<version>-<sha12>/   окружение каждого релиза
/opt/parser/current -> releases/...      активный релиз
/opt/parser/backups/                     закрытые snapshots перед обновлением
/var/lib/parser/config.yaml              рабочая конфигурация
/var/lib/parser/.env                     секреты
/var/lib/parser/.data/                   БД, lock, сессии, OAuth
```

Код принадлежит администратору; runtime-пользователь пишет только рабочие данные. `/var/lib/parser` принадлежит `parser`, права 0700; конфигурация, ключи и токены — 0600. Относительные пути в YAML считаются от его каталога. Все изменяемые пути должны оставаться вне `releases/` и попадать в `ReadWritePaths` units. Журнал `<storage.database>.usage.jsonl` резервируется отдельно от SQLite.

Установите адаптированные [parser.service](../deploy/parser.service), [parser.timer](../deploy/parser.timer) и [parser-web.service](../deploy/parser-web.service) в `/etc/systemd/system/`:

```bash
sudo install -m 0644 deploy/parser.service deploy/parser.timer deploy/parser-web.service /etc/systemd/system/
sudo systemctl daemon-reload
```

Команды выполняются из проверенного checkout. При изменении `DEPLOY_ROOT`/`DEPLOY_CONFIG` измените пути также в units: workflow не перезаписывает установленные units. Оба сервиса должны иметь одинаковые явные `User`/`Group`. До первого деплоя таймер оставляют выключенным. Другие cron-процессы, циклы и ручные веб-процессы этого экземпляра нужно остановить; один сервер использует общий `storage.lock_file`, веб-процесс дополнительно держит `<lock_file>.web`.

SSH-пользователь выкладки должен иметь право выполнить `sudo -n /usr/bin/python3.12` для загруженного установщика. Для другого `DEPLOY_PYTHON` нужен соответствующий абсолютный путь. Это привилегированный доступ к серверу; runtime-пользователю такое sudo не требуется. Используйте отдельный ключ выкладки и ограничьте управление релизными тегами.

## Веб-сервис

В рабочем YAML включите `web.enabled: true` и задайте `LEAD_WEB_TOKEN` длиной от 16 символов в серверном `.env`. Сервис также считается необходимым при включённых Telegram-уведомлениях с `claim_buttons` или `track_clicks`. Для трекера нужен `web.public_url`. По умолчанию привязка — `127.0.0.1:8080`; внешний доступ организуется через TLS-прокси или SSH-туннель. [Функции веб-страницы и кнопок](claims-web.md).

`parser-web.service` запускает `lead-parser web`, перезапускает процесс при сбое и даёт 60 секунд на корректную остановку. `ExecCondition` пропускает запуск, если веб-функции выключены. Команда `lead-parser web --config ... --check-enabled` только проверяет условие: код 0 — нужен запуск, 1 — выключено; она не обращается к сети и не создаёт БД.

Деплой запускает включённую веб-часть и ждёт до 30 секунд HTTP 200 на `/healthz` с ожидаемой версией пакета и схемой 2. Endpoint не требует ключа и не выдаёт содержимое заявок. Он проверяет доступность SQLite и веб-таблиц, но не соединение с Telegram или внешними API. Веб-слушатель кнопок использует getUpdates: второй listener того же бота запускать нельзя.

После первого успешного деплоя для автозапуска при перезагрузке выполните `sudo systemctl enable parser-web.service`. Если веб-функции выключены, сервис не запускается. Деплой не меняет состояние `enabled` units.

## Настройка GitHub

В environment **production**:

| Тип | Имя | Значение |
| --- | --- | --- |
| Secret | `DEPLOY_SSH_KEY` | Отдельный приватный ключ выкладки |
| Secret | `DEPLOY_KNOWN_HOSTS` | Проверенная запись ключа сервера |
| Variable | `DEPLOY_HOST` | DNS/IP сервера |
| Variable | `DEPLOY_USER` | SSH-пользователь выкладки |
| Variable | `DEPLOY_PORT` | Порт, по умолчанию 22 |
| Variable | `DEPLOY_ROOT` | По умолчанию `/opt/parser` |
| Variable | `DEPLOY_CONFIG` | По умолчанию `/var/lib/parser/config.yaml` |
| Variable | `DEPLOY_PYTHON` | По умолчанию `/usr/bin/python3.12` |

Ключ сервера проверяется через доверенный канал; для нестандартного порта запись known_hosts содержит `[hostname]:port`. Рабочие ключи VK, Telegram, OpenRouter, Google и почты остаются на сервере.

Администратор репозитория должен ограничить environment релизными тегами и защитить создание/перемещение тегов. Обязательные проверки `main`: `checks (3.12)`, `checks (3.13)`, `checks (3.14)`; [payload защиты ветки](branch-protection.json). Эти настройки требуют GitHub admin и не включаются изменением YAML. Обязательное подтверждение environment включает ручную остановку workflow перед SSH; для согласованной автоматической выкладки его не задают. [Правила environments GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

## Выпуск

1. Проверить серверные units, пути, доступы, backup и конфигурацию. При наличии ручного старого веб-процесса остановить его до первого обновления.
2. Убедиться, что CI выбранного `main` зелёный, `project.version` равна нужной стабильной версии, а изменения lock/export закоммичены.
3. Создать тег только на проверенном коммите, например:

   ```bash
   git fetch origin main --tags
   git tag -a v0.2.0 origin/main -m 'Release 0.2.0'
   git push origin refs/tags/v0.2.0
   ```

4. Дождаться успешного Deploy tagged release. Проверить SHA, `status: deployed`, `migration`, `web_required` и путь backup в `/opt/parser/current/deployment.json`. Для включённого веба проверить `systemctl status parser-web.service`, `journalctl -u parser-web.service` и `curl --fail http://127.0.0.1:8080/healthz` (адрес адаптировать к YAML).
5. После проверки интеграций оператор явно включает новое расписание: `sudo systemctl enable --now parser.timer`. Выкладка сохраняет состояние таймера и не включает выключенный сбор. Веб-часть при включённых кнопках начинает принимать callbacks сразу после запуска сервиса.

Тег выпуска не перемещают: исправления получают новый номер. Архив workflow хранится в артефакте `parser-release` 30 дней. Длительное хранение релизов и backup настраивается отдельно.

## Порядок обновления и восстановления

1. Подготовка окружения, проверка конфигурации и расположения рабочих файлов; проверка установленного веб-unit, если он нужен.
2. Остановка таймера; ожидание завершения parser.service без прерывания; остановка parser-web.service. Блокировки parser и web исключают параллельные ручные процессы новой версии.
3. Backup существующей SQLite через backup API, включая committed WAL. На временной копии проверяется явная миграция `1 → 2`; неизвестные схемы, изменения существующих объектов и незапланированные таблицы отклоняются.
4. Та же миграция применяется к рабочей БД от runtime-пользователя; схема сверяется с результатом на копии. Новая отсутствующая БД инициализируется схемой 2. Тексты, ключи лидов, очередь, номера строк Sheets, курсоры, существующие клики и отметки не переписываются.
5. Переключение `current`, запись квитанции, запуск нужного веба и проверка health; затем восстановление ранее активного таймера. Выключенные веб-функции останавливают старый веб-процесс.

При сбое **до попытки запуска новых сервисов** установщик восстанавливает прежнюю БД из backup, ссылку и прежние активные сервисы. Если новые процессы уже могли работать, автоматический откат данных не выполняется: сохраняются новый релиз и БД, таймер и веб останавливаются. Если systemd не подтвердил остановку, workflow сообщает об этом отдельно. Статус `prepared` не равен успешному деплою: перед возобновлением проверить процессы, БД, квитанцию и логи. Нельзя просто переключить код схемы 2 на старую версию, ожидающую схему 1.

Повтор успешно установленного текущего релиза возвращает его квитанцию. Неудачные неактивные каталоги сохраняются как `.failed-*`; активный каталог не переименовывается. Для ручной миграции и согласованного восстановления см. [эксплуатацию](operations.md). Восстановление старого backup после новых доставок может повторить отправки, поэтому требуется сверка с Sheets/Telegram.
