# Автоматическая выкладка по тегу

GitHub Actions запускает [deploy.yml](../.github/workflows/deploy.yml) при push тега вида `vX.Y.Z`, например `v0.2.0`. Обычный push в `main` выполняет CI без выкладки. Версия из тега должна точно совпадать с `project.version` в `pyproject.toml`, а отмеченный коммит должен входить в историю `origin/main`. Теги с суффиксами (`v0.2.0-rc.1`, `v0.2.0.dev0`) и ведущими нулями отклоняются проверкой релиза. Фильтр события использует [синтаксис workflow GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushbranchestagsbranches-ignoretags-ignore), строгую проверку версии выполняет `scripts/release_gate.py`.

Сначала повторно выполняется полный CI на Python 3.12–3.14. Затем workflow собирает wheel и архив с закреплёнными runtime-зависимостями, SHA коммита и SHA256 файлов. После успешных проверок архив передаётся по SSH на Linux-сервер с systemd. Установка создаёт отдельное окружение для релиза и переключает ссылку `current` после локальной проверки конфигурации и совместимости SQLite.

Это инструкция для подключения сервера. Наличие workflow в GitHub ещё не означает, что рабочий сервер и доступы настроены. Текущая версия проекта `0.2.0.dev0` намеренно не проходит проверку для тега `v0.2.0`: сначала нужен коммит с релизной версией.

## Сервер и рабочие данные

Подготовьте сервер с Python 3.12, модулями `venv`/`pip`, systemd и доступом к источнику Python-зависимостей. Установите системные библиотеки Chromium, если Avito использует локальный браузер. Для работы с подключённым CDP собственный браузер не требуется. Рабочий пользователь и группа в шаблонах — `parser`; каталог установки по умолчанию — `/opt/parser`.

Код и изменяемые данные размещаются отдельно:

```text
/opt/parser/
  releases/<version>-<sha12>/   wheel, manifest и отдельный .venv
  current -> releases/...      активный релиз
  backups/                    закрытые snapshots SQLite перед обновлением
/var/lib/parser/
  config.yaml                 рабочая конфигурация
  .env                        секреты интеграций
  .data/                      SQLite, lock и Telegram-сессия
  ...                         VK-токены и ключ Google
```

Каталог установки и файлы релизов должны контролироваться администратором; пользователь `parser` читает код и пишет только рабочие данные. Каталог `/var/lib/parser` принадлежит `parser`, права каталога — 0700, конфигурации, `.env` и ключей — 0600. Относительные пути в YAML считаются от его каталога, поэтому значения из `config.example.yaml` сохраняют данные вне релизов. Перед переносом существующего экземпляра сохраните его данные и прежние пути к БД, блокировке и сессии.

Один раз установите адаптированные [parser.service](../deploy/parser.service) и [parser.timer](../deploy/parser.timer) в `/etc/systemd/system/`, затем выполните `systemctl daemon-reload`. Service запускает `/opt/parser/current/.venv/bin/lead-parser --config /var/lib/parser/config.yaml`; браузеры Playwright ищет через `PLAYWRIGHT_BROWSERS_PATH=/opt/parser/current/.browsers`. Установщик берёт runtime-пользователя и группу из unit; у service должен быть явно задан `User`. При изменении путей в GitHub variables измените также unit: workflow не переписывает установленные units. Все записываемые приложением файлы должны попадать в `ReadWritePaths`.

До первой успешной установки оставьте `parser.timer` выключенным. Установщик сохраняет состояние расписания: он не включает новый таймер автоматически. Другие cron-задачи и ручные циклы для того же экземпляра должны быть остановлены; приложение использует один общий `storage.lock_file`.

SSH-пользователь выкладки должен иметь согласованное право выполнить `sudo -n /usr/bin/python3.12` для загруженного `deploy/install_release.py`. Если задан другой `DEPLOY_PYTHON`, в правиле sudo нужен именно этот абсолютный путь. Это привилегированный доступ: право запуска загруженного Python-кода от root позволяет изменять сервер, а ограничение sudo только именем интерпретатора не создаёт изоляции. Используйте отдельный ключ выкладки и ограничьте круг пользователей, управляющих релизными тегами и GitHub environment. Runtime-пользователю `parser` это право не требуется.

## Настройка GitHub

В репозитории создайте environment **`production`** и задайте в нём secrets и variables. Значения секретов вводятся в GitHub напрямую; их не нужно отправлять в чат, коммитить или вставлять в команды с записью в shell history.

| Тип | Имя | Значение |
| --- | --- | --- |
| Secret | `DEPLOY_SSH_KEY` | Отдельный приватный SSH-ключ пользователя выкладки |
| Secret | `DEPLOY_KNOWN_HOSTS` | Проверенная запись ключа SSH-сервера в формате `known_hosts` |
| Variable | `DEPLOY_HOST` | DNS-имя или адрес сервера |
| Variable | `DEPLOY_USER` | Пользователь SSH с правами выкладки |
| Variable | `DEPLOY_PORT` | SSH-порт, по умолчанию `22` |
| Variable | `DEPLOY_ROOT` | Каталог релизов, по умолчанию `/opt/parser` |
| Variable | `DEPLOY_CONFIG` | Рабочий YAML, по умолчанию `/var/lib/parser/config.yaml` |
| Variable | `DEPLOY_PYTHON` | Python для окружения релиза, по умолчанию `/usr/bin/python3.12` |

Ключ сервера для `DEPLOY_KNOWN_HOSTS` проверьте через доверенный канал, например консоль хостинга. Для нестандартного порта запись содержит `[hostname]:port`. Workflow проверяет host key; получение непроверенного ключа непосредственно перед соединением не заменяет эту проверку.

Ограничьте deployment environment релизными тегами и настройте правила репозитория для их создания по принятому порядку выпуска. Доступ к environment и защита ветки `main` настраиваются отдельно. Если добавить обязательное подтверждение environment, workflow будет ждать его перед SSH; для автоматической выкладки подтверждение не включают. Настройки и доступность правил описаны в [документации GitHub environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments). Рабочие ключи VK, Telegram, OpenRouter и Google остаются на сервере и не нужны CI.

## Выпуск версии

1. Измените `project.version` в `pyproject.toml` на стабильную версию, например `0.2.0`. Обновите `uv.lock` командой `uv lock` и экспорт зависимостей: `uv export --locked --no-dev --no-emit-project --no-header --output-file requirements.txt`.
2. Проверьте изменения и включите коммит в `main`. До первого клиентского запуска выполните условия [готовности релиза](release-readiness.md), включая согласованную проверку интеграций.
3. Убедитесь, что выбранный коммит содержит нужную версию, и отправьте соответствующий тег. Например, для уже подготовленного `origin/main`:

   ```bash
   git fetch origin main --tags
   git tag -a v0.2.0 origin/main -m 'Release 0.2.0'
   git push origin refs/tags/v0.2.0
   ```

4. Дождитесь успешного workflow **Deploy tagged release** в Actions. Проверьте SHA, версию и `status: deployed` в `current/deployment.json`, вывод шага установки и `journalctl -u parser.service` после следующего планового запуска. Квитанция `deployment.json` содержит также путь предыдущего релиза и backup. Архив выпуска доступен в артефакте `parser-release` этого workflow в течение 30 дней; для более долгого хранения сохраните его в принятом хранилище релизов.

Релизный тег обозначает неизменный коммит. Для исправления выпуска создавайте новую версию и новый тег, сохраняя историю предыдущего. CI проверяет код и локальные сценарии, но не обращается к рабочим API и не подтверждает качество живой модели.

После первой установки оператор проверяет рабочие настройки, проводит согласованный первый запуск и явно включает расписание: `sudo systemctl enable --now parser.timer`. Деплой сам не запускает сбор или доставку в рабочие интеграции.

## Обновление, сбой и откат

Установщик проверяет архив и готовит окружение релиза; Chromium скачивается только для включённого Avito без CDP/Dolphin. Затем установщик приостанавливает таймер и дожидается завершения активного `parser.service`. Под блокировкой приложения он делает snapshot существующей SQLite через backup API в `DEPLOY_ROOT/backups` и проверяет новую версию на копии БД. Рабочая БД, конфигурация, сессии и токены не переносятся в каталог релиза. Ссылка `current` переключается только после успешных проверок; ранее активный таймер запускается снова. Состояние `enabled` таймера не меняется.

Для существующей БД установщик сравнивает `PRAGMA user_version` и определения таблиц/индексов в `sqlite_schema` до и после проверки копии. При изменении схемы автоматическая выкладка прекращается: сначала нужна отдельно подготовленная миграция данных. Первичная инициализация отсутствующей БД проверяется на временной копии; рабочую БД установщик не создаёт.

При ошибке установки или проверки workflow завершается неуспешно. До переключения продолжает использоваться прежний релиз. Ошибка после переключения, но до попытки восстановления расписания возвращает прежнюю ссылку. Если ошибка возникла после попытки запуска таймера — при самом запуске или окончательной записи квитанции, — установщик останавливает расписание и оставляет новый релиз активным: запуск процесса уже мог начаться, и автоматически менять код в такой момент нельзя. Проверьте `systemctl status parser.service parser.timer`, ссылку `current`, квитанцию и вывод workflow перед ручным восстановлением. Статус `prepared` или повреждённая квитанция не считаются успешной выкладкой при повторном запуске.

Старые релизы и backups сохраняются; их срок хранения и очистка определяются отдельно. Повторная установка текущего релиза со статусом `deployed` возвращает его успешную квитанцию. Неудачная установка, которая не осталась активной, сохраняется в каталоге `.failed-...` внутри `releases`; обычный повтор выкладки может создать каталог релиза заново. Удалять такой каталог вручную перед повтором не требуется. Если не удалось выполнить автоматическое восстановление, сначала разберите состояние процесса, ссылки и расписания.

Для отката через этот pipeline верните нужное поведение кода отдельным коммитом в `main`, назначьте следующую стабильную версию и выпустите новый тег. Такой выпуск проходит тот же CI, backup и проверку совместимости на копии текущей БД. Уже использованный тег не переносится на другой коммит; отдельной команды реактивации прежнего каталога релиза нет.

Для ручного отката кода допустим только релиз, совместимый с текущей схемой SQLite. Одного переключения ссылки недостаточно: нужны остановка расписания, ожидание активного процесса, блокировка, backup и проверка старого кода на копии текущей БД. Порядок восстановления данных описан в [эксплуатации](operations.md#резервирование-и-восстановление). Автоматическая замена рабочей БД старым snapshot при откате кода не выполняется: она может повторить уже доставленные уведомления.

Выкладка обновляет один сервер с локальной SQLite. Она не вводит поддержку нескольких хостов или параллельных экземпляров приложения.
