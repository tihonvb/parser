# Миграция и эксплуатация

## Переход с прежнего main

1. Остановить cron/процесс; сохранить старую конфигурацию, `.env`, Telegram-сессию, `seen_leads.json`, VK JSON и сервисный ключ в закрытом каталоге. Сделать копию исходного листа Sheets. Не выкладывать backup в Git.
2. Установить новую ветку/проверенный commit и зависимости из lock. Сравнить свой YAML с `config.example.yaml`: новые `output.enabled`, `vk.token_mode`, `storage.database`, `storage.lock_file`, бюджеты и таймауты. Неизвестные/ошибочные поля отклоняются; поддержанные старые поля дополняются значениями по умолчанию. Если старый `output` не содержит `enabled`, доставка считается включённой.
3. В режиме VK ID использовать один `vk_token.py`. Свежий файл с `expires_at` принимается без лишнего refresh. Старый сырой JSON без срока требует одного refresh; получить надёжный срок задним числом нельзя. Старую попытку PKCE без времени начать заново. Если refresh отозван, выполнить `login/code`.
4. Для листа: `uv run --locked python fix_sheet.py --config config.yaml`. Это чтение и план без записи. Миграция поддерживает общий старый заголовок из 9 колонок; неизвестная схема останавливается. `--apply` сначала вызывает `duplicate_sheet`, затем сохраняет строки на **том же ID листа**, добавляя J:M. Дополнительные пользовательские колонки перемещаются вправо с сохранением видимых значений. Исходные формулы/форматы сохраняются в архивной копии; новый управляемый диапазон RAW содержит значения. Для более сложного документа подготовить явную ручную миграцию из backup, не перезаписывать неподходящий заголовок.
5. VK-ID восстанавливается из wall-ссылки; Avito-ID — из адреса объявления. Telegram username не позволяет надёжно восстановить числовой channel ID: технические поля остаются пустыми. При наличии проверенного сопоставления передать `--identity-map identities.json`: `{ "https://t.me/name/10": {"lead_id":"telegram:123_10", "source_id":"telegram:123"} }`. Не выдумывать ID; план сообщает число неразрешённых строк. Перед доставкой проверить дубли ключей и сохранность пользовательских колонок.
6. При первом `main.py` старые ID из `seen_leads.json` импортируются отдельно в `legacy_seen` ровно один раз на путь. Для них не создаются фиктивные тексты/вердикты и не повторяется доставка. Повреждённый JSON останавливает миграцию; восстановить backup, не заменять его пустой историей. Если старой истории нет, надо сверить источники/таблицу и восстановить её до первого сбора, иначе старые публикации могут снова стать кандидатами.
7. Запустить `--check-config`, затем согласованную проверку интеграций, затем плановое расписание. Сохранить отчёт первой проверки и идентификаторы назначения.

## Резервирование и восстановление

`main.py --backup NEW_PATH` использует SQLite backup API под процессной блокировкой: копировать только файл БД во время активной WAL-записи нельзя. Назначение должно быть новым файлом; права POSIX — 0600. База содержит исходные тексты/контакты и историю очереди: хранить закрыто, с установленным для проекта сроком хранения. Отдельно резервировать секреты и Telegram-сессию закрытым способом.

Для восстановления остановить расписание и убедиться, что процесса нет. Сохранить текущий комплект БД/WAL/SHM для расследования, заменить БД согласованным snapshot, убрать относящиеся к заменённой БД старые sidecar-файлы, проверить `--status` и соответствие зарезервированных строк Sheets. Восстановление более старой БД может повторить Telegram-отправки после точки backup; Sheets использует уже существующие технические ID, но структурное изменение строк надо устранить до возобновления. Не создавать две рабочие копии одной очереди с разными lock-путями.

Для отката кода возвращать только версию, поддерживающую текущую схему SQLite, либо одновременно восстанавливать согласованные БД/Sheets backup. Текущая схема 1; неизвестная будущая версия БД останавливает приложение. Старый main с JSON seen не совместим с новой очередью.

## Разбор сбоя

- `pending` ИИ: повтор запланирован; текст уже сохранён. После `max_attempts` состояние `review`, требуется разбор/`--retry-failed`.
- `failed` доставки: устранить доступ/схему, затем `--retry-failed`. Исправить сортировку/вставку в Sheets прежде, чем возвращать конфликтную строку в очередь.
- VK `5` — токен; `7`/`1051` — доступ/тип профиля, повтор транспорта не выдаст новые права. В `execute` неуспешные дочерние вызовы не считаются пустыми страницами. Транзитные ошибки ограниченно повторяются выборочно.
- Telegram `FloodWait:N`: канал неполон, собранная часть сохранена; повторить после паузы. Неудача одного канала не отменяет другой. Сбой подключения/очистки отражается отдельно, login при расписании не запрашивается.
- Avito `SourceBlocked`, `DetailLayoutChanged`, `SearchLayoutChangedOrUnrecognizedBlock`: различать отказ доступа и смену селекторов. Пустая выдача успешна только при распознанном индикаторе отсутствия результатов.
- `BudgetExhausted`/`complete:false`: остаток VK/TG продолжится с сохранённого места; не удалять cursor. Контрольная точка окна обновляется только после завершения участка. Avito и глобальный поиск остаются ограниченными поисковыми выборками.

`--status` содержит все сохранённые задания. Отключение интеграции/смена адреса останавливает соответствующую старую очередь, не удаляя её: это видно как незавершённые задания. Новые получатели не получают историю автоматически. `--deliver-only` позволяет восстановить обработку без API источников. Технические исключения логируются по классу/коду, без remote body, токенов, callback или содержимого рабочего лида. Специализированный `scripts/check_secrets.py` проверяет известные сигнатуры и приватные пути во всей Git-истории; это не доказательство отсутствия любого возможного секрета. Если обнаружен действующий секрет, сначала отозвать его, затем выполнять отдельную согласованную очистку истории.

## Защита main

Изменение защиты `tihonvb/parser/main` требует прав администратора. Подготовлен [точный payload](branch-protection.json) с обязательными `checks (3.12)`, `checks (3.13)`, `checks (3.14)`, одним review, сбросом устаревшего review, запретом force-push/удаления и применением к администраторам.

После успешного Actions для этих имён администратор выполняет:

```bash
gh api --method PUT repos/tihonvb/parser/branches/main/protection --input docs/branch-protection.json
gh api repos/tihonvb/parser/branches/main/protection
```

Проверить результат в Settings и невозможность обычного merge при упавшем check/без review; сохранить ссылку на успешный run. Эта настройка upstream не менялась из учётной записи с READ-доступом.
