# Миграция и эксплуатация

## Обновление с версии SQLite на пакетную структуру

Рефакторинг в `src/lead_parser/` сохраняет `PRAGMA user_version = 1`, таблицы, ключи, курсоры, получателей и зарезервированные строки. Повторно импортировать историю, пересоздавать БД или мигрировать актуальный 13-колоночный лист не требуется.

1. Остановить расписание и сделать snapshot через прежнюю команду backup; отдельно сохранить конфигурацию и секреты.
2. Установить проверенный commit, выполнить `uv sync --locked --no-dev`. Проект устанавливается как пакет; запуск отдельных файлов из `src/` не требуется.
3. Запустить `uv run --locked lead-parser --config /absolute/path/config.yaml --check-config`, затем `--status`. Сверить число кандидатов/заданий и сохранённые контрольные точки с отчётом до обновления.
4. Обновить команду планировщика на `/absolute/path/.venv/bin/lead-parser --config /absolute/path/config.yaml`. Старый `python main.py` продолжает работать через CLI-обёртку. Сохранять прежний `storage.lock_file` и один экземпляр расписания.
5. Возобновить обработку и проверить отчёт. Для первого восстановления очереди доступен `--deliver-only`.

Альтернатива консоли — `python -m lead_parser` из установленного окружения. Сборка wheel: `uv build --wheel`; wheel содержит пакет и синтетический evaluation-набор, конфигурацию и рабочие секреты размещают снаружи. Для wheel также нужно отдельно установить согласованные runtime-зависимости и Chromium, если используется обычный браузер Avito.

Старые библиотечные импорты (`from common import Lead`, `from storage import Store`) заменены пакетными: `lead_parser.core.models.Lead`, `lead_parser.infrastructure.persistence.sqlite.Store`. Корневые скрипты сохраняют совместимость запуска команд, а не прежний Python API. [Слои и точки расширения](architecture.md).

## Первичный переход с JSON-дедупликации

1. Остановить cron/процесс; сохранить старую конфигурацию, `.env`, Telegram-сессию, `seen_leads.json`, VK JSON и сервисный ключ в закрытом каталоге. Сделать копию исходного листа Sheets. Не выкладывать backup в Git.
2. Установить новую ветку/проверенный commit и зависимости из lock. Сравнить свой YAML с `config.example.yaml`: новые `output.enabled`, `vk.token_mode`, `storage.database`, `storage.lock_file`, бюджеты и таймауты. Неизвестные/ошибочные поля отклоняются; поддержанные старые поля дополняются значениями по умолчанию. Если старый `output` не содержит `enabled`, доставка считается включённой.
3. В режиме VK ID использовать `lead-parser vk-auth` и один менеджер `infrastructure.integrations.vk.oauth.TokenManager`. Свежий файл с `expires_at` принимается без лишнего refresh. Старый сырой JSON без срока требует одного refresh; получить надёжный срок задним числом нельзя. Старую попытку PKCE без времени начать заново. Если refresh отозван, выполнить `login/code`.
4. Для листа: `uv run --locked lead-parser migrate-sheet --config config.yaml`. Это чтение и план без записи. Миграция поддерживает общий старый заголовок из 9 колонок; неизвестная схема останавливается. `--apply` сначала вызывает `duplicate_sheet`, затем сохраняет строки на **том же ID листа**, добавляя J:M. Дополнительные пользовательские колонки перемещаются вправо с сохранением видимых значений. Исходные формулы/форматы сохраняются в архивной копии; новый управляемый диапазон RAW содержит значения. Для более сложного документа подготовить явную ручную миграцию из backup, не перезаписывать неподходящий заголовок.
5. VK-ID восстанавливается из wall-ссылки; Avito-ID — из адреса объявления. Telegram username не позволяет надёжно восстановить числовой channel ID: технические поля остаются пустыми. При наличии проверенного сопоставления передать `--identity-map identities.json`: `{ "https://t.me/name/10": {"lead_id":"telegram:123_10", "source_id":"telegram:123"} }`. Не выдумывать ID; план сообщает число неразрешённых строк. Перед доставкой проверить дубли ключей и сохранность пользовательских колонок.
6. При первом обычном запуске `lead-parser` старые ID из `seen_leads.json` импортируются отдельно в `legacy_seen` ровно один раз на путь. Для них не создаются фиктивные тексты/вердикты и не повторяется доставка. Повреждённый JSON останавливает миграцию; восстановить backup, не заменять его пустой историей. Если старой истории нет, надо сверить источники/таблицу и восстановить её до первого сбора, иначе старые публикации могут снова стать кандидатами.
7. Запустить `--check-config`, затем согласованную проверку интеграций, затем плановое расписание. Сохранить отчёт первой проверки и идентификаторы назначения.

## Резервирование и восстановление

`lead-parser --config config.yaml --backup NEW_PATH` использует SQLite backup API под процессной блокировкой: копировать только файл БД во время активной WAL-записи нельзя. Назначение должно быть новым файлом; права POSIX — 0600. База содержит исходные тексты/контакты и историю очереди: хранить закрыто, с установленным для проекта сроком хранения. Отдельно резервировать секреты и Telegram-сессию закрытым способом.

Для восстановления остановить расписание и убедиться, что процесса нет. Сохранить текущий комплект БД/WAL/SHM для расследования, заменить БД согласованным snapshot, убрать относящиеся к заменённой БД старые sidecar-файлы, проверить `--status` и соответствие зарезервированных строк Sheets. Восстановление более старой БД может повторить Telegram-отправки после точки backup; Sheets использует уже существующие технические ID, но структурное изменение строк надо устранить до возобновления. Не создавать две рабочие копии одной очереди с разными lock-путями.

Для отката кода возвращать только версию, поддерживающую текущую схему SQLite, либо одновременно восстанавливать согласованные БД/Sheets backup. Текущая схема 1 (она не изменена переносом кода в пакет); неизвестная будущая версия БД останавливает приложение. Старый main с JSON seen не совместим с новой очередью.

## Модель исполнения и ограничения

Приложение рассчитано на один сервер с локальными файлами SQLite/Telegram-сессии и общим `storage.lock_file`. `FileLock` предотвращает пересечение запусков этого экземпляра; транзакции и leases защищают очередь при восстановлении. Сетевой каталог или несколько хостов с независимыми lock-файлами не образуют поддерживаемый кластер. Для нескольких worker-процессов на разных хостах сначала нужен адаптер общей БД и согласованный механизм координации.

Google Sheets получает повторную запись в заранее закреплённую строку. Telegram Bot API работает с семантикой at-least-once при неопределённом результате отправки: успешное сообщение с потерянным HTTP-ответом может прийти повторно. Задания с подтверждённым успехом не повторяются, включая переоценку лида. Это эксплуатационные свойства доставки, сохранённые при смене структуры проекта.

`ai_confidence` — оценка модели, а не проверка человеком или вероятность заключения сделки. Для пользовательской разметки используйте `lead-parser stats --human-label SOURCE:ID --is-client yes|no`; человеческие и модельные показатели учитываются раздельно.

## Разбор сбоя

- `pending` ИИ: повтор запланирован; текст уже сохранён. После `max_attempts` состояние `review`, требуется разбор/`--retry-failed`.
- `failed` доставки: устранить доступ/схему, затем `--retry-failed`. Исправить сортировку/вставку в Sheets прежде, чем возвращать конфликтную строку в очередь.
- VK `5` — токен; `7`/`1051` — доступ/тип профиля, повтор транспорта не выдаст новые права. В `execute` неуспешные дочерние вызовы не считаются пустыми страницами. Транзитные ошибки ограниченно повторяются выборочно.
- Telegram `FloodWait:N`: канал неполон, собранная часть сохранена; повторить после паузы. Неудача одного канала не отменяет другой. Сбой подключения/очистки отражается отдельно, login при расписании не запрашивается.
- Avito `SourceBlocked`, `DetailLayoutChanged`, `SearchLayoutChangedOrUnrecognizedBlock`: различать отказ доступа и смену селекторов. Пустая выдача успешна только при распознанном индикаторе отсутствия результатов.
- `BudgetExhausted`/`complete:false`: остаток VK/TG продолжится с сохранённого места; не удалять cursor. Контрольная точка окна обновляется только после завершения участка. Avito и глобальный поиск остаются ограниченными поисковыми выборками.

`--status` содержит все сохранённые задания. Отключение интеграции/смена адреса останавливает соответствующую старую очередь, не удаляя её: это видно как незавершённые задания. Новые получатели не получают историю автоматически. `--deliver-only` позволяет восстановить обработку без API источников. Технические исключения логируются по классу/коду, без remote body, токенов, callback или содержимого рабочего лида. Специализированный `scripts/check_secrets.py` проверяет известные сигнатуры и приватные пути во всей Git-истории; это не доказательство отсутствия любого возможного секрета. Если обнаружен действующий секрет, сначала отозвать его, затем выполнять отдельную согласованную очистку истории.

## Защита main

Изменение защиты `tihonvb/parser/main` требует прав администратора. Подготовлен [точный payload](branch-protection.json) с обязательными `checks (3.12)`, `checks (3.13)`, `checks (3.14)`, одним review, сбросом устаревшего review, запретом force-push/удаления и применением к администраторам.

После успешного Actions для этих имён администратор выполняет:

```bash
gh api --method PUT repos/tihonvb/parser/branches/main/protection --input docs/branch-protection.json
gh api repos/tihonvb/parser/branches/main/protection
```

Проверить результат в Settings и невозможность обычного merge при упавшем check/без review; сохранить ссылку на успешный run. Эта настройка upstream не менялась из учётной записи с READ-доступом.
